GameMaster - Kenolab

Gamemaster is an easy Active Directory machine from Kenolab (https://www.kenolab.eu/welcome), created by Anh4ckin and PhoeniX. It involves SQLi, user enumeration, AS-REP roasting with Kerberoasting to get a crackable hash for a service account, ACL abuse and decrypting an RDG file to get the administrator password.

Recon

nmap

We start with a full port scan

The open ports show we are dealing with a Domain Controller: DNS (53), Kerberos (88), LDAP (389/636), SMB (445) and WinRM (5985/5986). There is also a web server on port 80, worth a closer look.

I’ll use netexec to generate the hosts file line and add it to /etc/hosts

SMB

Since we don’t have any credentials yet, we can start by trying to list the SMB shares using null and guest authentication. Both are disabled in this case

Port 80

There’s a website on port 80 with a /backups folder, but access to it is forbidden. The /search.asp page looks like a good target for SQL injection so let’s run sqlmap against it

Backup file

Thankfully, that wasn’t complicated, and sqlmap managed to dump the whole database. Nothing looked interesting, like credentials or password hashes, but one thing stood out: a backup file at /backups/backup_20260126-oldsite-frontend.bak. We can try to access it directly with the full url: http://10.253.163.14/backups/backup_20260126-oldsite-frontend.bak. Let’s download it locally

It’s a zip archive containing several pdf files. Nothing looked interesting in them, as they were all dummy text

Auth as iis_svc

User enumeration

One useful thing we can pull from those PDFs is the author field, which holds several names we can parse into usernames

Since we don’t know the username format, we can use username-anarchy. It takes a list of names in first last format and generates many common username formats, which we can then test with a tool like kerbrute to see which ones are valid

Running kerbrute against the dc with the generated usernames file returned 5 valid users

Let’s save these usernames into a file

AS-REP roasting

Now that we have valid usernames, we can try AS-REP roasting to see if any of them are vulnerable

Nice! We got the hash of marc.shadow, so let’s try to crack it with john. Unfortunately, it doesn’t crack

Kerberoasting through AS-REQ

Another thing we can try is this research from Semperis, which shows that an account with DONT_REQUIRE_PREAUTH set can be abused to kerberoast other users. We can do this easily with netexec using the --no-preauth-targets flag

It dumped the hash of the iis_svc user, and this time the hash cracked with john

Shell as lucas.morau

BloodHound

With valid credentials in hand, we can run BloodHound to gain a better understanding of the network and the permissions our users have

Looking at BloodHound, we can see that iis_svc has GenericAll over the IT OU

OU ACL abuse

GenericAll on the OU gives us control of the OU object itself, but not automatically of the objects inside it. To get that, we use Impacket’s dacledit to add an inheritable FullControl ACE for iis_svc (the -inheritance flag), so the rights propagate to the users and groups in the OU.

Back in BloodHound, the IT OU contains the Remote_Access group, and lucas.morau is a member of it. Since we granted ourselves FullControl on the OU with an inheritable ACE, that control should propagate to the objects inside it, including lucas.morau.

We can verify this with bloodyAD get writable, which lists every object we can modify. The output confirms we now have write access over lucas.morau, including DACL: WRITE and OWNER: WRITE, which effectively means full control of the account.

lucas.morau is the only user in the OU besides iis_svc that shows up with DACL: WRITE and OWNER: WRITE. The other users are missing, so let’s find out why by listing the OU’s users with their adminCount and group membership:

Every other user in the OU has adminCount: 1. These are protected accounts (members of privileged groups). They don’t inherit ACEs from their parent OU, which is why the dacledit warning mentioned adminCount=1. lucas.morau and iis_svc are the only ones without it, which makes lucas.morau our target: he is in Remote_Access, which should give us WinRM access.

Password reset

Let’s use bloodyAD to change lucas.morau’s password. GenericAll allows other approaches too (shadow credentials, for example), but I’m lazy and this is the quickest :)

Now let’s connect over WinRM with winrmexec and grab the user flag.

Shell as Administrator

RDCMan file

On the desktop there is a node13.rdg file. This is a Remote Desktop Connection Manager (RDCMan) configuration file that stores saved RDP connections, including usernames and DPAPI-encrypted passwords.

DPAPI decryption

The .rdg file stores its saved password as a DPAPI-encrypted blob. DPAPI ties the encryption key to the user who created it, and Windows makes that key available to any process running as that user. Since we are running as lucas.morau, who owns the file, we can decrypt the blob directly from our PowerShell session with ProtectedData.Unprotect and the CurrentUser scope, with no extra tooling and no need to know his password. This reveals the administrator’s password.

Let’s connect again with winrmexec, this time as the administrator, and grab the root flag.
